# Кейс 3. Разработка интеллектуальной системы генерации и аудита безопасности SQL-запросов

> **Цель:** создать MVP многоагентной системы, которая по текстовому описанию задачи автоматически генерирует SQL-запросы для PostgreSQL, проверяет их на уязвимости безопасности и итеративно исправляет до получения одобренного результата — с полным логом аудита для пользователя.

## Подробнее о задаче

GreenData — российский разработчик low-code-платформы для создания корпоративных ИТ-систем (CRM, ERP, ITSM и др.), лидер рейтинга российских low-code-платформ 2025 года по версии «Сколково» и TAdviser. Платформа активно использует PostgreSQL как основную СУБД.

Аналитики и разработчики компании регулярно формулируют SQL-запросы для отчетов, выгрузок и автоматизации процессов. Проблема в том, что вручную написанные или сгенерированные запросы могут содержать как логические ошибки, так и серьезные уязвимости безопасности: SQL-инъекции, избыточный доступ к чувствительным данным, операции без условий фильтрации. Без специализированной проверки это остается незамеченным до момента инцидента.

> **Ваша задача** — создать систему, в которой SQL-запрос не просто генерируется, но и обязательно проходит автоматизированный аудит безопасности перед тем, как попасть к пользователю. Предпочтительная архитектура — итеративный цикл «генератор → судья → исправление», однако команды могут предложить альтернативный подход, если он обеспечивает сопоставимый уровень безопасности и точности.

**Ключевой исследовательский вопрос:** как сделать так, чтобы генератор действительно учился на замечаниях судьи от итерации к итерации, а не воспроизводил те же ошибки?

Разработанное решение планируется интегрировать в реальный рабочий процесс аналитиков GreenData.

## Условия выполнения

### Командам передаются:

- доступ к тестовому инстансу GreenData с реальной схемой PostgreSQL-базы (без прямого доступа к базе, но с возможностью установить необходимые таблицы локально);
- шаблон baseline.

### Требования и ограничения:

- Диалект только PostgreSQL (обязательно); поддержка Oracle и MS SQL — опционально.
- Система не исполняет запросы самостоятельно — цикл завершается при одобрении судьи или исчерпании лимита итераций.
- Данные тестовой базы могут содержать условно конфиденциальную информацию, поэтому обращаться с ними надо соответственно.
- Допускается использование публичных LLM API.

### В рамках решения кейса вам будет необходимо:

- Изучить схему тестовой PostgreSQL-базы GreenData и сформировать ее машиночитаемое представление.
- Собрать или синтезировать датасет пар «описание задачи на естественном языке → SQL-запрос», включающий как эталонные безопасные примеры, так и запросы с типичными уязвимостями.
- Разработать модуль генерации: выбрать и реализовать метод формирования запросов (промпт-инжиниринг, RAG или fine-tuning); провести первичные тесты точности генерации (Execution Accuracy).
- Разработать модуль аудита безопасности («судья»): реализовать классификацию уязвимостей с оценкой риска по шкале от 0 до 10 и формированием конкретных пояснений по каждому найденному замечанию.
- Спроектировать и реализовать архитектуру системы — предпочтительно итеративный цикл «генератор → судья → исправление» или обоснованную альтернативу с сопоставимым уровнем безопасности.
- Убедиться, что генератор действительно учитывает замечания судьи от итерации к итерации — и не воспроизводит уже выявленные ошибки.
- Реализовать прозрачный лог для пользователя: какие риски были обнаружены, сколько итераций потребовалось, почему финальный запрос признан безопасным.
- Оценить эффективность системы: доля одобренных запросов, среднее число итераций до одобрения, динамика снижения оценки риска.
- Подготовить структурированный отчет: описание архитектуры, метрики качества, анализ ошибок и направления развития.
- Подготовить демонстрацию работы системы в реальном времени для защиты: ввод описания задачи → автономная работа системы → выдача финального безопасного SQL с логом аудита.

## Ожидаемый результат

### Технологические требования:

- Обязательно: Python 3.10+, PostgreSQL для тестирования.
- Рекомендуется: LLM API (OpenAI / YandexGPT / локальная модель), LangChain или аналог для RAG.
- Оформление кода: Git-репозиторий, requirements.txt / pyproject.toml.
- Интерфейс — на усмотрение команды: Streamlit, FastAPI, CLI, телеграм-бот или иной.

Классы уязвимостей, которые система должна уметь выявлять (ориентир, не исчерпывающий список):

| Класс уязвимости | Риск | Описание и пример |
|---|---:|---|
| SQL Injection (классический) | 10 | Динамическая конкатенация пользовательского ввода без параметризации. Позволяет выполнить произвольный SQL |
| Union-based Injection | 9 | Использование UNION SELECT для извлечения данных из других таблиц, не предусмотренных запросом |
| Time-based blind Injection | 8 | Использование pg_sleep() или тяжелых вычислений для разведки структуры БД через время ответа |
| Privilege Escalation через EXECUTE | 8 | Вызов EXECUTE с динамически формируемой строкой внутри функций с правами SECURITY DEFINER |
| Избыточный SELECT * | 5 | Выборка всех полей таблицы, включая потенциально чувствительные (пароли, токены, персональные данные) |
| UPDATE / DELETE без WHERE | 9 | Модификация или удаление всех строк таблицы из-за отсутствия условия фильтрации |
| Прямой доступ к чувствительным полям | 6 | Запрос полей password_hash, token, ssn, card_number без маскировки или ограничения прав |
| Неограниченный LIMIT / отсутствие пагинации | 4 | Запрос без LIMIT может вернуть миллионы строк, вызвав DoS на уровне БД или приложения |
| PL/pgSQL: небезопасный EXECUTE (доп. уровень) | 9 | В хранимых процедурах: динамический SQL через EXECUTE format(...) без использования USING для параметров |

Необходимо предоставить заказчику:

- Работающую систему генерации и аудита SQL-запросов — программное решение с обязательной автоматизированной проверкой на безопасность, задокументированное в Git-репозитории.
- Лог аудита — отображение финального одобренного запроса с описанием всех выявленных рисков и хода их устранения.
- Live-demo на защите: ввод описания задачи на естественном языке → автономная работа системы → финальный безопасный SQL с логом.
- Сравнительный анализ — демонстрация кейса, где исходная версия запроса содержала уязвимость, а итоговая успешно прошла проверку.
- Структурированный отчет: архитектура решения, метрики качества генерации (Execution Accuracy), оценка эффективности судьи, статистика снижения рисков.
- Презентацию для защиты перед заказчиком (10–15 слайдов).

## Оценивание

Оценивание решения кейса складывается из финальной защиты проекта перед представителями компании GreenData (оценки выступления) и оценки подготовленных и сданных артефактов работы.

Для успешной защиты необходимо набрать не менее 42 баллов по основным критериям оценивания:

| Критерий | Описание | Баллы |
|---|---|---:|
| Точность генерации SQL | Execution Accuracy на тестовом наборе составляет не менее 70%; результат измерен и задокументирован | 15 |
| Покрытие классов уязвимостей | Судья выявляет не менее 5 классов уязвимостей, по каждому формирует объяснение и оценку риска по шкале от 0 до 10 | 25 |
| Работа итеративного цикла | Генератор действительно учитывает замечания судьи и исправляет запрос от итерации к итерации; одни и те же ошибки не воспроизводятся повторно | 25 |
| Аналитика и отчетность | Представлена динамика оценки риска по итерациям, среднее число итераций до одобрения и содержательный анализ ошибок | 15 |
| Прозрачность для пользователя | Лог аудита понятен аналитику без погружения в код: видно, какие риски найдены, сколько итераций потребовалось и почему финальный запрос одобрен | 10 |
| Воспроизводимость и качество кода | Код размещен в репозитории; инструкция по запуску присутствует и работает; решение воспроизводимо независимо от автора | 10 |
| Обоснованность архитектурных решений | Команда объясняет выбор архитектуры, LLM, метода генерации и подхода к аудиту; рассмотрены альтернативы; решение соответствует формату MVP | 10 |

Блокирующий критерий: участие в итоговой защите.

Без участия в финальной защите работа команды оценивается в 0 баллов. На защите должны присутствовать все члены команды

| Критерий | Описание | Баллы |
|---|---|---:|
| Качество live-demo и презентации | Демо воспроизводится стабильно; показан кейс с уязвимостью и ее устранением. Работа команды слаженна, решения аргументированы, даны ответы на вопросы. Команда демонстрирует распределение ответственности, вклад участников равномерный (если в зоне ответственности студента работа выполнена на значительно отличающемся от остальной команды уровне, его индивидуальный балл может быть повышен или снижен) | 10 |

Важно: командам выставляется незачет, если по итогам защиты и оценки артефактов не набрано 42 баллов по критериям.
